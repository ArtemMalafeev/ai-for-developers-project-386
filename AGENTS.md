# Инструкции для работы с репозиторием

## Назначение проекта

Это учебный сервис бронирования встреч («Календарь звонков»). Репозиторий организован как pnpm-монорепозиторий:

- `apps/web` — клиент на Vue 3, TypeScript и Vite.
- `apps/backend` — API на Fastify и TypeScript.
- `scripts/smoke.mjs` — сквозная проверка запуска обоих приложений.

Основные пользовательские сценарии описаны в `README.md`: владелец создаёт типы встреч, пользователь выбирает свободный слот, а владелец просматривает записи.

## Требования к окружению

- Используйте Node.js `26.13.0`, pnpm `12.16.1` и hk `2.11.0` (версии зафиксированы в `mise.toml`).
- Установите зависимости из корня командой `pnpm install`.
- Команды запускайте из корня репозитория, если явно не указано иное.
- Отдельные приложения являются приватными workspace-пакетами с именами `apps-web` и `apps-api`.

## Часто используемые команды

```bash
# Разработка: Vite и Fastify запускаются параллельно
pnpm dev

# Проверка стиля во всех workspace-пакетах
pnpm -r lint

# Проверка типов во всех workspace-пакетах
pnpm -r type-check

# Полная проверка приложения и прокси /api
node scripts/smoke.mjs

# Все проверки из mise
mise run check
```

Команды конкретного пакета можно запускать через фильтр:

```bash
pnpm --filter apps-web dev
pnpm --filter apps-web build
pnpm --filter apps-api dev
pnpm --filter apps-api build
```

Для форматирования клиентского кода используйте `pnpm --filter apps-web format`; проверка без изменений — `pnpm --filter apps-web format:check`.

## Архитектура и локальная разработка

- Backend слушает `127.0.0.1:3000` и предоставляет health-endpoint `/health` и `/api/health`.
- Vite слушает стандартный порт `5173`; запросы `/api` проксируются на backend через `apps/web/vite.config.ts`.
- Smoke-тест сам запускает оба dev-сервера. Перед ним остановите вручную запущенные процессы на портах 3000 и 5173.
- Переменные окружения сейчас не требуются. Если они появятся, документируйте имена и безопасные значения в README, не добавляя секреты в Git.

## API-контракт и генерация

`packages/contracts/src/main.tsp` — источник API-контракта. При изменении API сначала правьте TypeSpec, затем запускайте из корня `pnpm contracts:generate` и коммитьте обновлённые артефакты:

- `packages/contracts/openapi/openapi.yaml`;
- `packages/api-client/src/generated/`;
- `apps/backend/src/generated/`.

Не редактируйте эти артефакты вручную. Проверяйте их актуальность командой `pnpm contracts:check`. CI повторно запускает генерацию и завершает проверку ошибкой, если сгенерированные файлы отличаются от закоммиченных.

## Правила изменения кода

- Сохраняйте TypeScript в строгом режиме и существующую структуру workspace.
- Для новых API-маршрутов обновляйте backend и клиентский proxy/вызовы согласованно.
- Пользовательские компоненты и логику интерфейса размещайте в `apps/web/src`; серверную логику — в `apps/backend/src`.
- Соблюдайте настройки ESLint, oxlint и oxfmt. Сначала исправляйте код, затем запускайте lint и type-check.
- Не редактируйте вручную содержимое `apps/web/dist` и `apps/backend/dist`: это артефакты сборки. Проверяйте, не попали ли они в коммит.
- Не изменяйте workflow Хекслета и не переименовывайте репозиторий без отдельной необходимости.
- Не добавляйте зависимости без объяснимой потребности; после изменения `package.json` обновляйте `pnpm-lock.yaml` командой `pnpm install`.
- Старайтесь делать небольшие тематические коммиты. В описании изменений указывайте, что проверено.

## Проверка перед завершением задачи

Перед передачей результата:

1. Запустите `pnpm -r lint`.
2. Запустите `pnpm -r type-check`.
3. Если менялись маршруты, запуск или связка frontend/backend, запустите `node scripts/smoke.mjs`.
4. Для клиентских изменений при необходимости дополнительно выполните `pnpm --filter apps-web build`.
5. Просмотрите `git diff` и убедитесь, что в изменениях нет секретов, временных файлов и нерелевантных артефактов сборки.

Если какая-либо проверка не запускается из-за отсутствующей зависимости или внешнего ограничения, укажите это явно вместе с точной командой и сообщением об ошибке.

## GIT

- Коммит требует явного подтверждения пользователя. Push требует отдельного явного запроса. Разрешение в текущей сессии учитывается при следующих шагах той же работы.
- Сообщение коммита пишется по Conventional Commits, описание на русском, в scope имя шаблона, например `fix(nodejs-package): убрать console.log`.
- Каждый коммит ссылается на связанный с ним тикет.

## Agent skills

### Issue tracker

Задачи и спецификации хранятся в GitHub Issues; для работы используйте `gh`. См. `docs/agents/issue-tracker.md`.

### Triage labels

Используются стандартные метки `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human` и `wontfix`. См. `docs/agents/triage-labels.md`.

### Domain docs

Репозиторий использует структуру с одним контекстом (single-context): корневой `GLOSSARY.md` и общие ADR в `docs/adr/`. См. `docs/agents/domain.md`.
